## 0. 适用范围与术语纠偏

**适用对象**：非银行支付机构（持《非银行支付机构支付业务许可证》）的支付系统研发交付，以及商户侧/平台侧涉及支付接入、账户、分账、对账的系统研发。银行侧核心系统归 finance profile。

**术语纠偏（重要）**：

1. **清算 ≠ 结算**：清算（Clearing）是计算参与方债权债务关系（信息处理，不动钱）；结算（Settlement）是完成资金实际划转（所有权转移）。先清算后结算，或清算结算一体化。研发中把"日终对账批处理"叫"结算"属术语误用。
2. **不存在"支付牌照"单一称谓**：真实牌照为《非银行支付机构支付业务许可证》，按业务类型分网络支付/银行卡收单/预付卡发行与受理三类（§1.1）。
3. **"二清"是违规形态而非业务模式**：无牌机构归集商户资金再分发即"二清"，属监管打击对象；合规替代是"分账"（持牌机构体系内的多方清分，§3.4）。

## 1. 支付监管基线（强制层）

### 1.1 牌照与监管框架演进

| 时间 | 法规/事件 | 对研发交付物的意义 |
|---|---|---|
| 2010 | 《非金融机构支付服务管理办法》（央行 2 号令） | 首次发牌，确立三类业务许可 |
| 2016 | 非银行支付机构风险专项整治 | "断直连"启动：支付机构断开与银行直连 |
| 2017 | 网联（NUCC）成立 | 网络支付经网联/银联集中转接 |
| 2019-01 | 备付金 100% 集中存管央行 | 支付机构不得挪用/占用/借用客户备付金（资金流向系统设计的硬约束） |
| 2023-12 | 《非银行支付机构监督管理条例》（国令 768 号） | 行政法规层级监管，反垄断与业务分类调整 |
| 2024-05 | 《非银行支付机构监督管理条例实施细则》 | 注册资本金要求、业务分类重划 |

**三类业务许可**：网络支付（互联网/移动支付）、银行卡收单（线下 POS/线上收单）、预付卡发行与受理。跨境支付另需外管局跨境外汇支付业务许可。

### 1.2 反洗钱（AML/CFT）研发义务

- **大额交易报告**：单笔或当日累计 ≥5 万元人民币（或等值外币）→ 报告央行反洗钱监测分析中心（系统须有大额交易识别与上报模块）。
- **可疑交易监测**：快进快出、金额与身份不符、频繁变更交易对手、跨境异常、夜间/节假日集中——须落地为规则引擎特征。
- **客户风险评级 + 名单筛查**：联合国制裁名单/公安部恐怖组织名单/央行红通名单的实时筛查接口。

### 1.3 数据合规

> 个人金融信息分级（JR/T 0171 C1-C3）、加密与去标识化义务（个保法 §51）、PIA 评估（个保法 §55/§56）、密评（GB/T 39786）等**立法条款与门禁映射归 `industry-profile-finance.md`**，本文件不重复展开；支付侧落地仅需在 `payment.conf` 的 `--privacy` 词表中追加支付特有敏感字段（卡号/CVV2/磁道/交易密码，见 §2 映射表第 1 行）。

- **支付特有敏感数据**（研发落地清单）：银行卡号、身份证号、手机号、交易密码——加密存储、脱敏展示、访问控制、审计日志。
- **卡号处理行业基线**：PCI DSS（卡号存储加密、传输 TLS、脱敏）为支付行业特有国际基线；国密场景算法选型叠加 finance 的 `CRYPTO_PROFILE=gm`。
- **外卡收单合规**（业务机理）：VISA QSP / Mastercard PF 认证、拒付（Chargeback）Visa 120 天窗口与再请款→预仲裁→仲裁流程（详见知识库 `references/waika-shoudan-analysis.md` §3.4）。

## 2. 清算与账务核心机理（pay-clearing 内核）

### 2.1 结算模式选型

| 模式 | 特点 | 适用场景 | 研发要点 |
|---|---|---|---|
| RTGS 全额实时 | 逐笔全额、实时、无信用风险 | 大额支付 | 逐笔状态机、头寸实时监控 |
| DNS 净额批量 | 批次轧差、延迟、有信用风险 | 小额高频 | 批处理窗口设计、轧差算法 |
| Hybrid | RTGS+DNS 结合 | 现代主流 | 两引擎并存+队列管理 |

### 2.2 央行支付系统对接参数

| 系统 | 结算方式 | 金额特征 | 运行时间 |
|---|---|---|---|
| HVPS 大额 | RTGS | 无下限 | 工作日 8:30-17:00 |
| BEPS 小额 | DNS | 单笔 ≤5 万 | 7×24 |
| 超级网银 | 实时 | 单笔 ≤5 万 | 7×24 |
| CIPS 跨境 | RTGS+DNS 混合 | — | 5×24+4h |

**研发含义**：支付路由须按金额/时效/运行时间选通道；日切点（如银联 23 点）是批处理与账务周期设计的关键约束。

### 2.3 对账与差错处理（研发必修）

**三方对账**：银行对账单 ←→ 支付机构交易流水 ←→ 商户订单。

| 差错类型 | 处理 | 系统模块 |
|---|---|---|
| 长款 | 挂账→核实→退还/冲正 | 差错工单+挂账科目 |
| 短款 | 挂账→核实→追款/补扣 | 同上 |
| 单边账 | 核实原始交易→补记/冲销 | 对账差异引擎 |
| 重复交易 | 保留一笔→其余冲正 | 幂等+冲正接口 |
| 金额不符 | 以银行侧为准→调整 | 差异调整流程 |

**标准流程**：日终对账文件生成→自动逐笔匹配→差错识别分类→人工核实（大额/异常）→差错处理→结果确认归档。

### 2.4 账务核心设计（复式记账）

- **铁律**：有借必有贷、借贷必相等；资产=负债+所有者权益。
- **科目体系**：资产（银行存款/备付金存款/应收款项）、负债（应付款项/客户备付金/预收款项）、权益、损益（手续费收入/通道成本/利息）。
- **分录示例（用户充值 100 元）**：借 银行存款-备付金账户 100 / 贷 客户备付金-用户A 100。
- **试算平衡**：日终校验所有科目借贷发生额合计相等；不平衡→账务差错→挂账→次日调整。
- **生产级一手参考**：蚂蚁账务清算域（热点账户缓冲记账/归类码多账套/四项资金核对/流动性调拨，知识库 `ant-ledger-domain-frameworks.md`）。

## 3. 支付系统技术实现（pay-infra 内核）

### 3.1 通道对接差异（选型必读）

| 通道 | 产品形态 | 研发注意 |
|---|---|---|
| 银联全渠道 | UPOP 网关、快捷 Token、代扣代付、二维码 | 报文 ISO 8583 系、签名验签 |
| 网联 | 协议支付、网关、条码 | 断直连后网络支付必经 |
| 银行直连 | 各行 API | 各行限额/签名差异大 |
| 微信/支付宝 | Native/JSAPI/H5/小程序/APP/当面付 | 异步通知回调的幂等处理 |
| Stripe/Adyen/PayPal | REST API | 与国内支付模型差异（授权-捕获两段式） |

### 3.2 支付方式实现要点

- **快捷支付**：四要素鉴权（姓名+身份证+卡号+手机号）+短信验证；Token 化（EMVCo Tokenisation）；签约/解约/支付/解约全流程状态机。
- **协议支付**：先签约后免密扣款、周期扣款（subscription）。
- **代扣/代付**：批量代扣（工资/保险）、单笔代付（提现/退款）的批处理与单笔通道分离。

### 3.3 账户体系设计

- 银行 I/II/III 类账户的功能与限额差异。
- 平台二级账户：平台总账户+用户子账户、虚账户/实账户映射。
- **分账体系**：实时分账 vs 延迟分账、多方分账规则引擎、分账比例动态配置——合规前提是分账在持牌体系内完成，否则构成"二清"。
- 内部账户族：客户账户、内部过渡户、清算户、损益户、在途资金户。

### 3.4 支付安全工程

- **幂等性**：支付超时处理、冲正机制、对账补单——支付系统所有写操作必须幂等（重试安全）。
- **风控**：规则引擎、设备指纹、行为分析、实时拦截。
- **加密**：卡号 PCI DSS 加密存储、TLS 传输、敏感数据脱敏。

### 3.5 流程编排：长事务链路的架构选型（pay-orchestrator 内核）

> 吸收来源：金墨数客《支付系统为什么必然走向 Flow 编排》（2026-09-21，https://mp.weixin.qq.com/s/t2_QpE-DmJ4HKFicDvsCPA）；框架版本事实以官方 releases 为准（本文不写死易漂移版本号）。通用验证口径（时间缝隙/逻辑割裂/悬空状态等十维）见 `domain-knowledge.md` 流程编排节，本节只记支付特化判断与选型知识。

**长事务体感（跨境 B2B 出款 12 步）**：参数校验→幂等校验→余额冻结→风控扫描→AML/制裁名单筛查→渠道路由→锁汇（FX 报价+锁定）→渠道出款→等 SWIFT 网络（小时~2 天，中间行可能退回）→等 Nostro 到账确认（~1 天，可能短款）→收款行入账（~1 天，账号错则退回）→通知商户+对账。12 步中 4 步跨天异步等待、3 步可能挂起等人工（风控/合规/锁汇过期重报价）——支付流程复杂度不在步骤多，而在步骤间的不可控时间缝隙；流程编排引擎本质是管理这些缝隙（挂起时持久化上下文，外部事件按 business_key 唤醒续跑）。

**无引擎反模式四特征**（探查期风险信号——主流程 Service/回调 Controller/定时扫表 Job 三文件形态）：

1. **逻辑割裂**：同一笔业务的流转规则散落三文件，改一处要想着另外两处；
2. **补偿靠记忆**：退款补偿在主流程与回调里各写一遍，漏一处就是资损；
3. **悬空状态**：风控超时等 UNKNOWN 态只能靠人工捞数据；
4. **无执行历史**：只知道当前 status，不知道何时/何步/卡多久（排查 20-40 分钟且依赖工程师经验；引擎看板 10-30 秒新人可查）。

**不用引擎的等效方案**（Stripe atomic phases 模型，2017 公开）：长流程切成若干原子阶段（每阶段一个本地事务）+ 每阶段末持久化恢复点 + 后台任务与业务写入同事务落库（Transactional Outbox 防"提交后未入队"）+ 请求带幂等键（重复请求返回首次结果）——自己补齐这几件事等效于手工实现一个轻量流程引擎。

**三大阵营选型**（九维度横评摘要：适用规模/性能/长生命周期/Saga/可视化/学习曲线/运维/开发体验/典型场景）：

| 阵营 | 代表 | 长生命周期 | Saga | 运维成本 | 典型场景 |
|---|---|---|---|---|---|
| BPMN 引擎 | Camunda 8 / Flowable / Activiti | 强 | 支持 | 高（独立部署；Camunda 7 社区版已停止维护，8 自管生产需商业许可） | 审批流/人工任务 |
| 微服务编排 | Temporal / Netflix Conductor | 极强（事件溯源恢复） | 原生支持 | 高（独立集群部署） | 支付/Saga/长链路 |
| 轻量 SDK | LiteFlow / Spring Statemachine | 弱（长事务需二开） | 不支持 | 低（SDK 嵌入、规则可热更新） | 风控规则/计费/本地多步校验 |

一句话建议：现有代码能稳定跑+新边缘业务变复杂→先试点微服务编排（逐用例替换+feature flag+蓝绿，不一次性切换）；高并发瓶颈+DB 扫表拖垮+状态难维护→全面迁移是划算的技术升级；只是本地多步校验/计费规则→轻量 SDK 足够，不引入集群。

**相反决策同一逻辑**（选型方法论：先回答"瓶颈在哪"）：Coinbase 弃自研 Saga 改用 Temporal——痛点是 Saga 路径组合爆炸，代码化程序化处理失败正好解决；Netflix Maestro 评估三方案（升级 Conductor/采用 Temporal/自研重写）后反向选自研——痛点是单步开销与 exactly-once 保证，日处理超百万任务下耦合外部调用是不必要的风险，用 outbox 模式重写后性能提升约百倍。两者结论相反，决策逻辑一致。

**Workflow as Code 开发纪律**（用 Temporal 类引擎的项目直接消费）：

- **确定性三红线**（Workflow 方法体内）：禁网络/IO 调用（重放会重复执行→重复扣款，副作用全部封装进 Activity）；禁本地时间与随机数（重放分支漂移，用引擎等价 API）；禁本地多线程（线程调度不可重放，用引擎并发原语）。
- **Activity 绝对幂等**：引擎默认对 Activity 指数退避重试，用 WorkflowId 做全局防重键；精细化超时（总时长+单次执行时长）；耗时极长的用心跳机制（Worker 宕机时引擎凭心跳丢失立刻换机重试）。
- **补偿栈**：每成功执行一步就把对应回滚动作压栈，业务失败时逆序弹出执行；引擎保证回滚中途宕机重启后继续补偿，不出现"部分回滚"悬空态——这是自研引擎最难做对的一点。
- **长流程版本演进**：用 Worker/Task Queue 版本路由（旧流程的任务路由给旧版 Worker，灰度丝滑），不用代码内 getVersion 双分支（时间久了变考古现场）。
- **性能与数据安全**：payload 只传 ID/URL 引用不传大对象（入参出参都序列化持久化，有 MB 级上限）；敏感数据（卡号/金额）Worker 端加密、Server 端只存密文（明文事件历史是金融红线）；按业务线/优先级拆分 Task Queue 独立扩缩容（支付与批处理不共队列）。

**自研轻量 Flow 六模块**（评估自研时的完备性清单）：① 流程定义（节点+边+补偿配置，DB 存储可热更新不发版）② 执行引擎（流程实例+上下文容器+节点调度器+表达式分支）③ 状态管理（实例表+节点执行表，business_key 异步唤醒）④ 异常处理（重试次数+退避策略+节点级/流程级超时+逆序补偿，配置化不改代码）⑤ 可观测（逐步开始/结束时间、入参出参、异常堆栈，任意 business_key 查完整链路）⑥ 运维（定时扫 WAITING 实例+手动重试/跳过/终止，运营自助干预）。

**探查关注点**（生成流程 ①.5 消费）：识别项目编排形态与割裂信号——同一业务键的状态写入是否散落三文件、悬空态有无兜底任务、回调幂等键在不在；编排形态结论写入特征卡与 reference-manual 时须附代码证据。

**门禁联动**：§5-① 幂等人工核对按本节细化三查——幂等键设计（回调/重试/并发下防重）、补偿单一来源（退款/冲正不在多处重复）、悬空状态出口（UNKNOWN 态有兜底任务或告警）。流程引擎类依赖（temporal/liteflow/camunda 等）尚无框架规则集，探查以依赖清单为准，不进 `ACTIVE_FRAMEWORKS_HINT`（防死信号）。

## 4. 条款 → 门禁映射（仅列支付特有差额）

金融业通用条款（JR/T 0171/0197/0223、GB/T 39786 密评、等保三级、银监发 40 号等）的门禁映射见 `industry-profile-finance.md` §2，本文件不重复。以下为支付业务机理对应的差额项：

| # | 业务/技术要求 | 承担门禁 | 状态 |
|---|---|---|---|
| 1 | 卡号/身份证/支付密码等敏感字段扫描（PCI DSS + JR/T 0171 C3） | `--privacy`（PRIVACY_EXTRA_PATTERNS 追加 CVV2/磁道特征；关键词含支付密码） | ✅🟡 词法层 |
| 2 | 国密算法（SM2/SM3/SM4，银联/密评场景） | `--crypto`（CRYPTO_PROFILE=gm） | ✅🟡 词法层 |
| 3 | 敏感个人信息处理前 PIA（个保法 §55/§56） | PIA_REQUIRED（compliance 层） | ✅ 启用后 |
| 4 | 发布产物完整性（NIST SP 800-218 PS.2） | `--release-sign`（RELEASE_SIGN_REQUIRED） | ✅ 启用后 |
