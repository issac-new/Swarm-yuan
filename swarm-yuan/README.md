## 文档边界与读法

本文是 swarm-yuan 的唯一设计文档：只回答系统是什么、为什么这样设计、怎么落地、凭什么有效。操作命令查 `docs/usage-manual.md`，演化过程与决策史查 `docs/design-evolution.md`，上游运行时基线查 `docs/upstream-baseline.md`，数字口径真值在 `swarm-yuan/assets/facts.conf`（机器对账）。

读法：第一、二章给判断依据（要不要用、为什么需要）；第三章是躯干（每层机制与检查）；第四章把机制映射到文件；第五章给适用边界；第六章收口。数字、来源、验收明细统一收在附录，正文不罗列。

术语只消歧三条（其余见使用手册术语表）：**生成物**与**目标技能**是同一实体的双名，生成视角叫生成物，交付使用后叫目标技能；**门禁**是 precheck 的词法结构检查，**验证**是测试与审查的语义核验，两者不是一回事（第三章 3.4/3.5 推导）；正文中的**组件库、地图、零件目录**同指目标技能里的 reference-manual 清单。

# 一、What：它是什么

**swarm-yuan 是一个生成器：对任意代码仓库跑一次，产出一个项目专属的研发能力技能（目标技能）；此后该项目的一切 AI 编码都由这个技能执勤。**

系统的全部内容可以收成一条链，本文就是这条链的逐环展开：

```
①认知项目的结构与关系 → ②整理工程规范
→ ③结合框架最佳实践与既有业务实现 → ④形成组件库与拼装式编排模式
→ ⑤吸收开发者的实际研发习惯 → ⑥装配成目标技能
→ ⑦用目标技能完成日常研发、测试、验证、交付（结合既有测试案例与工具）
→ ⑧使用中按具体问题迭代成长 →（项目演进，回到①重新同步）
```

链条上每一环都对应一份实物：认知出**地图**（组件/接口/数据清单）、**关系边集**与**配方**（业务功能清单 + 任务拼装序列）；规范出**铁律、三值规则与门禁配置**；习惯出**开发偏好**；装配出**目标技能六段目录**；执勤靠**门禁与验证**；成长走**两条演化通道**。后文每层对这条链的一段负责：第二章论证它为什么必须存在，第三章讲它怎么被做出来并保证可信，第四章说它落在哪些文件上。

两体结构是全文反复用到的基本形：**生成器厚、目标技能薄**。探查知识允许厚，只在生成时刻消费一次；目标技能必须薄，它在每次开发会话里重复加载，每个字节都是税。税有机器预算，超了 CI 就红（口径见附录 A）。

# 二、Why：为什么需要它

**AI 写代码的瓶颈已经不在会不会写，在懂不懂项目。** 不认识项目就动手，于是改了不该改的文件，升级了不该升级的依赖，重复造了已有组件的轮子，检查靠人逐行 review。缺陷不在生成，在认知。

把这些失败拆开看，恰好分成两类，而两类失败需要完全不同的工具。这是全文最重要的一次推导：

- **不懂规矩**：不知道只读区不能改，不知道稳定组件不能动，不知道提交要带测试。这类失败有词法和结构特征，机器能抓。
- **想错逻辑**：规矩全守了，但算法写错、边界漏了、契约悄悄破坏。这类失败没有模式可匹配，只能真跑测试、独立审查才能发现。

于是系统有两件核心工具：**门禁**管第一类（模式匹配，事前事中拦截），**验证**管第二类（语义核验，事后证明），另设独立**验证器**证明门禁本身没有形同虚设。把它们混为一谈（比如指望门禁抓逻辑错误）是这类系统最常见的自欺。

为什么不直接用现成方案？lint 规则包只覆盖第一类失败的一小部分，且不带项目认知；人工写项目文档没有机器校验，写完就开始腐烂；让 AI 裸写等于放弃拦截。三者分别缺了链条上的认知、检查、约束环节。

再做一次反证，链条缺任何一环会怎样：

- 缺认知，不探查直接生成规则，门禁照抄通用模板，与项目无关，AI 第一件事就是绕过它；
- 缺组件库检查，清单是幻觉凑出来的，照着拼装必然崩盘（实证见 3.1）；
- 缺约束，认知停在文档里，AI 读完照犯，提示词约束不了行为（3.4 展开）；
- 缺验证，门禁全绿不代表逻辑正确，绿着交付缺陷；
- 缺成长，项目演进三个月后技能过时，系统退化为一次性脚手架。

从问题与反证里长出四条执政理念，每条都要求一个可验证的兑现机制，兑现点在第三章逐一指认：

1. **拼装式开发**：新功能 = 既有稳定单元拼装 + 最小新增胶水。零件目录来自探查，拆分正确性有管束链（3.5）。
2. **特征卡立法、门禁执法、验证器司法**：特征卡定义项目的应然，门禁检查代码的实然，独立验证器证明检查本身有效。三者互不越界；这是叙事隐喻，真实拓扑按实现（第四章）。
3. **诚实降级**：运行时没装就显式披露，不假装全深度接线；权限边界一律 fail-closed，宁拦不错放。
4. **AI 全自动、零手动配置**：生成由 AI 一键完成，使用时研发人员对 AI 说话；bash 命令只是排查与 CI 的备份通道。

# 三、How：怎么做到

> 本章是全文躯干，按链条顺序分六层。每层开头先交代它与上一层的关系。读完应能回答：链条上每一环由什么机制兑现、这个机制由什么检查兜底、检查的证据落在哪。

## 3.1 认知层：先认识，再行动

第二章确立了认知先行。本层回答：认知怎么做成，做出来的地图凭什么可信。

**认知的产物是三张图，不是一份读后感。** 探查期先做项目形态判定，再按判定出的维度全量穷举，产出三样东西：一是**地图**，组件、接口、数据三类清单，统一两列表（路径 + 说明与约束），路径供机器执法，说明列写 AI 读代码后的理解与稳定性标注；二是**关系边集**，谁依赖谁的机器可读记录，先由脚本机械提取 import 边，AI 再补调用、路由、消息等语义边；三是**配方**，业务功能清单加高频任务的拼装序列，每个配方五要素（触发场景、前置查询、复用件、胶水、门禁与验证）。三者分工：地图回答有什么零件，边集回答谁依赖谁，配方回答怎么拼。

**组件库必须过三道检查才准出厂。** 零件目录一旦失真，拼装式开发整体失效：

1. **防漏：计数核验。** 清单条目数不得少于机械枚举数的 95%，每个维度独立核验。这条红线有来历：某真实项目初版地图只列了 10 个组件，代码库实际有上百个模块，样本化填充只覆盖了一成。95% 就是那次之后定的。
2. **防伪：路径核验。** 清单和配方里登记的每个路径逐个验存在；检出幻觉路径直接阻断激活，技能停在 draft 态，全量门禁不解锁。
3. **防过时：稳定性审计。** 标注"稳定/禁止改"的单元用三个机械信号复核（近期变更次数、被引用数、有无同名测试），标注与事实冲突就提示复核。这一级只提示不阻断，因为信号是启发式，判断留给人。

框架与技术栈的最佳实践不在地图里罗列，以**框架规则集**的形式按探查结果激活：探到哪个框架，才注入哪个框架的约束与门禁片段；每条规律必须在项目代码里找到证据才实例化，找不到就剔除并记录反例。既有业务功能实现编目进配方的功能清单，每个功能注明由哪些组件拼成、走哪个接口、落哪些数据、有没有测试，成为后续同类任务的先例。

## 3.2 规范层：规矩从哪来

认知层产出了项目是什么样。本层回答：项目的规矩从哪来，以什么形式进入技能。

规范有三个来源，按可信度排序。**已写下的**：AGENTS.md、CLAUDE.md、记忆中的规则与偏好，直接提取。**实际做的**：git 历史的行为统计（提交前缀、分支命名、共变文件、热点文件、测试提交占比），脚本机械出初稿，AI 审读后才采纳；统计事实不等于规范，书面规则优先。**推导出的**：探查期从编排约束与只读判定推导的项目特有规则初稿，例如生成代码目录禁手改。

三源汇合后按形式分工：规矩的**表述**进技能铁律段，引用来源而不写死值；规矩的**执行**进三值规则与门禁，一条规则的 allow/prompt/forbid 是可机读的数据，不是散文；规矩的**参数**进 conf 文件，机器嗅探出初稿、AI 补语义项，每个值带来源注释。表述与执行分离是刻意的：地图与铁律管"是什么"，规则与门禁管"应当怎样"，两区不混写。

## 3.3 装配层：生成与出厂

前两层的产物要装配成目标技能。本层回答：装配怎么做，什么状态下技能算可信出厂。

生成的分工红线是**机械出初稿、AI 审判断**。脚本只做信号可信的事：枚举、拷贝骨架、渲染配置初稿、核验计数；判断性环节必须 AI 做：特征卡填值、规律实例化、习惯采纳。反过来的分工都是事故源：脚本假装能判断质量，或者 AI 重复跑机械流程。

出厂有一道状态门，把前面所有检查变成硬门槛。骨架生成后是 draft 态，全量门禁禁用；三关全过才翻 active 解锁：占位符清零、清单路径零幻觉、计数核验达标。draft 可断点续传，active 必须全绿。不用一次性否决令，用状态区分"还在填"和"可执勤"。

装配还要守厚薄分界。进目标技能的每份文件都按每会话重复付税计价，认知面、入口文件、概念数量各有预算上限，CI 机器断言。预算是恒等式：新内容进技能，必须给既有段落瘦身腾位，只增不减就是膨胀。

## 3.4 执勤层（上）：门禁管"不懂规矩"

技能出厂后开始执勤。执勤的前一半是门禁：词法与结构层面的模式匹配，事前事中拦截。

门禁在三个位置拦截。**写之前**：hooks 拦"无 spec 写源码"，拦命中 forbid 规则的命令；拒绝消息必带替代方案，拒绝即指路，AI 能自动改道。**改之时**：每次编辑过范围与敏感度检查。**收尾时**：按任务类型选门禁序列执行。多门禁同跑有执行纪律：按"构建、测试、契约、复用、一致性、分层、文档、安全、依赖"的顺序串行，任一步失败即停，不拿后面的绿掩盖前面的红；每步留痕到执行账本，审查时据此确认序列真跑过，而不是声称跑过。

门禁分 strict、warn、advisory 三级，这不是技术洁癖，是诚实分层：能给出稳定 fail 信号的才配阻断交付；信号有噪声的降级为提示，由 AI 判断采纳；判断不了的（例如"这次复用是否贴合场景"）不假装能判，门禁输出三问引导，AI 自查并留痕供审查回放。机械只管信号可信处、判断留给 AI 并留痕，这条边界是全系统防自欺的总阀门。

门禁自身的复杂度也被门禁管住：门禁总数冻结在预算上限内，新增须等额删除，配置变量与认知面同理。声称帮项目降复杂度的东西，自己不能失控。另有一条失败方向教义：权限边界 fail-closed，fail-open 只允许发生在还有下层强制兜底的地方（例如 hooks 失败不阻断，因为命令还要过门禁）。

## 3.5 执勤层（下）：验证管"想错逻辑"

门禁管不住逻辑错误。执勤的后一半是验证：语义层面的真跑与独立审查，外加对检查者自身的检查。

验证有三件。**测试真跑**：执行项目测试命令看退出码，检出"零用例空跑通过"的假绿；测试文件本身进清单维度做计数核验，测试体系存在而没配运行命令会显式提示。**独立审查**：以第三方视角重看产物，审查记录落盘才算数，口头"已审查"不算。**司法验证**：独立验证器用双态样例证明每个门禁真的能检出违规（违规样例必须被抓、合规样例必须放行），并锁定命令行行为逐字节等价。司法的诚实边界要说破：样例是构造的，曾在 5 个真实项目上漏过 3 个真 bug，所以样例验证之外还要真实项目回归；外部效度未达阈值前，本文不宣称"守护代码合规"（验收口径见附录 D）。

验证依赖留痕。调用、决策、门禁执行、拦截各有一本账，账本之间链式锚定，上游被改则全链可检出；审计按"一个用户目标加一个验收边界"核对闭环。没有这些账，"验证过"就只是声称。

**门禁与验证如何接力，看拼装管束这一个实例就够了。** 拼装式开发的核心风险是拆错：把本该复用的当成新写（重复造轮子），或者把该保护的改了（偷改稳定单元）。管束链按时间接力：spec 阶段先声明切分方案（复用哪些既有单元、新增哪些胶水、为何不能复用）；编码时门禁查新增胶水与稳定单元重名（重名即失败，应直接复用），查稳定单元被改而未声明（失败），查稳定单元的下游被波及（提示声明）；配方引用的复用件路径验真（幻觉零件在此被杀）；测试兜底逻辑正确性。机械能判的全部判了，判不了的诚实降级为 AI 自查留痕。这条链就是第二章那句"两类失败两种工具"的完整展开。

## 3.6 成长层：项目变了，技能跟着变

前五层把技能立起来了。本层回答：它凭什么不腐烂。

成长有两条触发通道。**结构通道**：项目指纹（文件数、扩展名分布、目录校验和）在会话开始时自动比对，变了就给出变化范围，只对该范围局部重探查，单条更新清单，落新基线；更新有 last-good 红线，条目骤降过半视为探查失败，保留旧清单。**问题通道**：使用中解决的新问题，一个新的复用解法、一条新发现的约束、一个踩过的坑，按三选一沉淀（进清单、进配方、进规则），每次沉淀留决策记录。前者防"项目变了技能没变"，后者兑现"按具体问题迭代成长"。生成器自身吸收外部方法论走同一条纪律：调研、评审、落地为条件或引导，全程留痕。

成长的预算约束与装配同一条：成长 = 预算内替换。新知识进来，必须有旧知识出去，或者税不增。否则不是成长，是膨胀。

## 3.7 衔接总表：没有一个概念是孤立的

上六层引入的每个核心概念，都能指出它诞生在哪、被谁消费、由谁检查、回流到哪。这张表是全文的自检表，也是设计没有孤儿的证据：

| 概念 | 诞生 | 消费方 | 检查兜底 | 回流 |
|---|---|---|---|---|
| 地图（组件库） | 3.1 探查穷举 | 编码时按图复用 | 计数核验 + 路径验真 + 稳定性审计 | 指纹变化后局部更新 |
| 关系边集 | 3.1 机械提取 + AI 补语义 | 探查"谁依赖某件"；稳定单元下游传播 | 抽样核验断边 | 变化后重建 |
| 业务功能清单 | 3.1 归纳 | 同类任务的先例库 | 配方结构执法 | 问题沉淀追加 |
| 任务配方 | 3.1 三源提取 | 探查先查配方，编码按配方拼装 | 五要素结构执法 + 引用路径验真 | 问题沉淀追加新配方 |
| 特征卡 | 探查期提取 | 门禁配置的参数源 | 出厂门三关核验真实性 | — |
| 开发偏好 | 3.2 行为观察 + 书面规则 | 执勤全程遵守 | 偏好节存在性执法 | 记忆写回闭环 |

| 指纹基线 | 装配期末 | 结构变化感知 | last-good 红线 | 更新后落新基线 |
| 问题沉淀 | 使用中随时 | 清单、配方、规则三载体 | 决策记录留痕可审计 | 回流执勤 |

## 3.8 完备性：凭什么就是这些机制

最后回答一个元问题：机制清单凭什么完备且互不冗余。答案是一个封闭的类型空间。全部机制所操作的实体、关系、动作登记在三份类型目录里（`assets/ontology/`，计数见附录 A），每条关系都有机器锚，关系的实例可验证存在。每个机制必须能回答"我实现哪条关系"，答不出就是孤儿，删掉或先补定义。

新机制入场走四问：引入什么实体，产生什么关系，关系的机器锚是什么，锚失效怎么检测。走完四问，实现通常收敛为一个字段加两处对账点，没有多余设计。历史上全部"文档声称与实现漂移"的缺陷，根源都是无锚的关系，所以锚先行，实现跟后。

# 四、实现：机制落在哪些实物上

设计到此完整。本章只做一件事：把机制映射到文件，一页说完。

**生成器侧**（本仓库 `swarm-yuan/`）：探查方法论与填充规范在 `references/`，门禁实现与规则数据在 `assets/`，生成与核验脚本在 `scripts/`，独立验证器在 `verifier/`。生成流程的逐步行事与机械/AI 分工详见 `references/generation-flow.md`。

**目标技能侧**（生成产物，六个目录）：SKILL.md 是每会话入口（预算封顶）；references/ 装地图、配方、工作流与项目文档（含开发偏好）；assets/ 装 spec 等模板；scripts/ 装门禁与工具；rules.d/ 装三值规则；hooks/ 与 settings 把技能挂进宿主。逐文件规格与命令清单见使用手册，不在此罗列。

三权分立的实物对应：立法 = 特征卡与清单（内容）；执法 = precheck 门禁 + hooks（条件）；司法 = verifier 目录（独立验证）。与宿主的分工同样固定：宿主管 agent 循环与沙箱，技能只管项目上下文、业务规则、操作边界，不碰宿主内部。

读者双轨：SKILL.md 写给 AI（零手动配置铁律），使用手册写给人（命令与排查）。

# 五、When：何时用、何时不用

| 适用 | 不适用 | 替代 |
|------|--------|------|
| 团队协作（≥2 人） | 个人脚本、一次性原型 | AI 裸写 |
| 中大型项目（≥80 文件） | 极小改动（typo 级） | 直接改 |
| 强监管、合规交付 | 无 AI 辅助的纯人工开发 | 传统 lint/test |
| 长期维护（技能须跟项目演进） | 只要门禁不要认知设施 | 单文件门禁脚本 |
| 小项目要基础门禁（lite 档） | | |

不建技能的轻量替代三选一：把单文件门禁脚本拷进项目配 conf 直接跑；传统 lint 加 Git hooks；一次性任务直接对 AI 说需求。

对外叙事守祛魅红线：不说"100% 可靠"，说"已验证组件 + 受约束生成 + 独立校验"；引用数字标口径与归属（清单计数是某个项目的探查产物，不是技能自带指标）；"三权分立"对外用时标注是叙事隐喻。本质一句话：bash 脚本加 Markdown 挂在 AI 编码助手的 hooks 上，写代码前拦截，交差时独立验证，外加本地观测。

# 六、核心总结

回到那条链。全文主张收成三句话。

**必要性**：链条缺一环，失败模式已在第二章逐环点名。缺认知则规则无根，缺检查则清单失真，缺约束则认知白做，缺验证则绿着交付缺陷，缺成长则三个月过期。

**充分性**：链条每一环有机制（第三章），每个机制有检查（3.7 衔接总表），每个检查有实物与证据（第四章与附录 D）。充分性不靠形容词，靠逐格可点。

**自证**：本文声称"降复杂度的东西自己不能失控"，于是把自己置于同一套约束之下：数字统一由 facts.conf 对账，正文不藏手抄口径；声称的机制都被 CI 跑过；每个设计取舍都能在决策史里查到全文。一份能约束自己展开方式的文档，才有资格约束 AI 写代码的方式。读懂这一句，就读懂了 swarm-yuan。
