## 一、文章调研结论（净增量判定）

文章十二节核心内容与 swarm-yuan 现状的对账：

| 文章内容 | swarm-yuan 现状 | 判定 |
|---|---|---|
| 编排演进五阶段（硬编码→状态字段→状态机→流程引擎→持久执行） | domain-knowledge 无此领域；支付档无编排维度 | **净增量** |
| 跨境出款 12 步链路、"步骤间不可控时间缝隙"本质 | 支付档 §2 有清算机理但无长事务链路视角 | **净增量** |
| 四痛点（状态撕裂/面条代码/Saga 补偿/可观测性）+ 无引擎反模式四特征（逻辑割裂三文件/补偿靠记忆/悬空状态/无执行历史） | 分布式节有幂等/一致性/Outbox 单行，无编排视角 | **净增量**（与既有行交叉引用不重复） |

| 三大阵营九维度选型矩阵 + Coinbase/Netflix 相反决策案例 | 无 | **净增量**（选型方法论：先答"瓶颈在哪"） |

| Temporal 高性能四大机制（分片/内存匹配/黏性执行/Append-Only） | 无 | **不吸收**——引擎内部实现细节，非项目研发交付消费面（吸收口径：机制服务于用引擎的项目，内部机制对目标技能无消费点） |

1. **`references/domain-knowledge.md`** 新增"流程编排（长事务）"节（分布式节后）：十维验证表（编排形态/时间缝隙/逻辑割裂/幂等/补偿/悬空状态/执行历史/断点恢复/无引擎等效/重放确定性）——通用化，任何长事务系统探查期可验证，`--domain` 门禁消费。该档随技能分发（UNIVERSAL_FILES）。
2. **`references/industry-profile-payment.md`** 新增 §3.5 流程编排（pay-orchestrator 内核）：支付特化——12 步链路体感、反模式四特征、Stripe 等效方案、三大阵营选型表+一句话建议、Coinbase/Netflix 相反决策、Workflow as Code 开发纪律（确定性三红线/Activity 幂等/补偿栈/版本路由/payload 纪律）、自研六模块、探查关注点（生成流程 ①.5 消费）、门禁联动（§5-① 细化三查）。该档按需 `--industry payment` 加载，不进 UNIVERSAL_FILES（不触发生成物字节预算）。

1. **不新建方法论档**：文章是领域工程知识非 AI 开发方法论，domain-knowledge（通用规律）+ 行业档（支付特化）双落点已覆盖消费面；新建档需过 R52 四步清单+map 行+分派可达，成本不对等收益。
